第一遍对着 PPT 读每页的“口语稿”，把整个故事串起来。第二遍读“理解与取舍”，弄懂为什么这样设计；这部分供备课，不需要全部念。第三遍只看每页的三个关键词，用自己的话讲出来。

技术词可以这样说：dsh 读字母“D、S、H”；pnpm 读“P、N、P、M”；AGENTS.md 直接说“项目说明文件”；system prompt 说“系统上下文”；supersede 说“旧记录退役”。不必反复读 API 全名。

## 第 1 页｜封面：dsh-memory

**记住三个词：项目约定、跨会话、自动维护。**

### 口语稿

老师好，我是陈悦祺。我的项目是 dsh-memory，给 DeepSeek Harness 增加跨会话的项目记忆。

我关注的是一个具体问题：我们和编程助手讨论过的项目约定，换一个会话以后，怎样继续使用？而且这些约定后来可能改变，保存下来的旧信息也需要更新。

这次我围绕这个问题，完成了原生插件开发、可靠性验证和三组对照实验。下面先从使用场景讲起。

### 理解与取舍

dsh 是运行 Agent 的宿主，负责模型调用、工具和会话等基础能力；dsh-memory 是装在其中的插件。可以把关系理解为“编辑器与扩展”，不是两个独立聊天机器人。

所谓记忆，是保存在模型外部的结构化记录。没有训练模型，也没有把事实永久写入模型参数。AI 协作分工会在最后说明，开场不必先列工具和版本号。

**衔接：**“先看为什么仅仅保存一份项目说明，还没有完全解决问题。”

## 第 2 页｜需要跨会话维护的项目知识

**记住三个词：没有信息、手动更新、自动更新。**

### 口语稿

比如，一个项目最初用 npm，后来决定统一改成 pnpm。如果新会话没有拿到之前的信息，助手就只能重新询问，或者说不知道。

一种很实用的办法，是把约定写进 AGENTS.md。只要文件维护得及时，它完全可以工作。但如果我们已经在对话里改了规则，文件还保留旧内容，助手仍可能按照旧规则回答。

dsh-memory 想做的，就是把这部分维护自动化：从对话里提取值得长期保留的信息，在约定改变时更新记录，再让新会话读到它。所以我要验证的，不只是“能不能记住”，还有“更新是否有效、额外成本有多少”。

### 理解与取舍

这页的三个方案，是“没有持久资料”“人工维护资料”“自动维护资料”。静态文件并不是差方案；它简单、透明、成本低。插件增加了自动化，也增加模型误抽取、陈旧记录和调用费用等问题。

不要说“所有 Agent 每次都会完全失忆”。更准确的是：**新会话必须通过某种机制获得历史知识**，本项目提供其中一种机制。

**衔接：**“为了把自动维护接进实际会话，我采用了宿主原生插件的方式。”

## 第 3 页｜工程范围与设计取舍

**记住三个词：复用宿主、轮末执行、限定范围。**

### 口语稿

这里有两个主要选择。第一，我采用 dsh 的原生插件接口，复用现有的事件、模型调用和存储服务。这样项目可以集中处理记忆本身，不必再维护一套独立服务；代价是需要适配 dsh 的接口。

第二，自动抽取主要放在每轮对话结束时。开发中发现，命令行进程退出太快，等到整个会话销毁时再保存，有时已经来不及。轮末的钩子可以等待任务完成，所以更适合作为主路径。

但这个选择也有成本：用户可能要多等一次抽取调用。后面的实验会同时报告效果和调用量。

### 理解与取舍

“钩子”就是宿主在某个时刻通知插件执行代码。`agent/turn-stopping` 表示本轮将结束；它的可等待性，让保存工作有机会在退出前完成。它不是“后台永不阻塞”，也不保证断电或强制结束时零丢失。

原生方式减少了单独搭建服务的工作，但牺牲了一些跨宿主可移植性。没有测试原生与 MCP 的性能差异，不要说“原生一定比 MCP 快”。

这页虽列了副插件，你可以直接略过名称，保持主线；第 12 页再带一句即可。

**衔接：**“先看一条真实记录，理解保存和重新读取分别发生了什么。”

## 第 4 页｜真实记录：一次抽取与一次跨上下文召回

**记住三个词：抽取、落盘、引用。**

### 口语稿

左边是一次真实小试验。输入告诉系统，项目统一使用 pnpm。插件把它整理成一条“项目约定”，保存到当前工作区的记忆库里。

右边重新建立了宿主上下文，再问这个项目用什么包管理器。模型回答 pnpm，并引用了一条记忆编号。这个编号能够对应到保存的记录。

这里也要说明，静态项目文件在这道题上同样答对了。因此，这一页证明的是保存和召回这条链路可以工作，还不能证明自动记忆比静态文件更好。

### 理解与取舍

“落盘”意味着信息保存在磁盘中，不只存在于某个进程的变量里；后续进程才能重新读取。“schema v5”是本项目记录的存储结构版本，不是模型版本。

本页来源是受控小试验，编号为 **#fe61379f**。新版操作视频来自另一轮真实网页运行，编号是 **#748a4179**。两者对应相同类型场景，但不是同一次运行。不要把 PPT 的记录说成视频截图，也不需要背编号。

引用可以帮助定位记录，但不能独立证明事实真实或仍然有效。比如有编号的旧规则，仍可能已经过期。

### 播放视频前后怎么说

**播放前：**“下面用约两分十八秒的 v0.5.1 网页录像，展示安装、保存、设置长期记忆、查看、新会话召回和取消。右侧的小鲸鱼是操作向导，画面是真实 dsh 网页，等待做了剪辑。”

**播放后：**“刚才的网页演示保持默认自动抽取，同时用工具显式管理长期记忆。取消长期保留不是删除，内容仍在；新会话召回的那一轮没有调用查看工具。接下来解释这些动作背后的实现。”

视频不必重复口述旁白。若时间不允许播放，可说“完整操作录像已随材料提交”，继续到下一页。

## 第 5 页｜插件架构

**记住三个词：抽取、治理、注入。**

### 口语稿

整个流程可以分成三步。

第一步是抽取。插件接收会话事件，积累对话文本，在满足条件的轮末调用一次辅助模型，把适合长期保留的信息整理成结构化候选。

第二步是治理和存储。候选不能直接全部塞进去，还要判断是不是重复、是否替代旧约定、属于哪个工作区，以及需不需要批准。

第三步是读取。新会话要回答问题时，插件选择相关且有效的记忆，放进系统上下文，让回答模型使用。用户还可以通过五个工具查看、删除、主动保存、批准和设置持久保留。

所以，模型负责理解对话，代码负责记录管理和执行边界；这两部分缺一不可。

### 理解与取舍

以 npm 改 pnpm 为例，辅助模型需要理解“这是规则改变”，返回结构化结果；代码随后检查它引用的旧编号是否属于本次允许处理的记录，再执行存储变更。不能因为模型输出了一个编号，就允许它修改任何项目的记忆。

抽取输出分为三个部分：

| 字段 | 含义 | 例子 |
|---|---|---|
| new | 新的长期信息 | 项目统一使用 pnpm |
| reinforce | 再次确认已有信息 | 用户换一种说法重复同一约定 |
| supersede | 将旧信息退役 | 原来的 npm 规则已经失效 |

去重有两层：抽取模型理解语义，存储层用规范化文本和词项包含度兜底。检索则结合关键词重合和衰减后的有效置信度，**没有使用 embedding 或向量数据库**。

“成功后推进增量游标”可以理解为做一个“处理到这里”的书签。保存失败时不移动书签，下次合格触发才有机会重试；这不等于有一条退出后仍持续运行的可靠消息队列。

五个工具的中文含义记住即可：list 查，forget 删，extract 主动提取，approve 批准，pin 设置或取消持久保留。没有要求你把五个函数名连续念完。

**衔接：**“把这条流程跑通之后，更重要的是检查它在出错时会不会把记忆弄坏。”

## 第 6 页｜可靠性修复与验收

**记住三个词：装得上、不串项目、更新不丢失。**

### 口语稿

这页是工程里比较关键的部分。

首先是别人能不能装起来。开发机上有已经构建好的文件，并不代表从 Git 安装也能用。项目补上了安装时的构建脚本，并在干净环境里检查生成的入口。

其次是工作区边界。项目 A 的规则不能随便混到项目 B，自动抽取只能更新当前项目的记录。

最后是新旧规则替换。比如 npm 改成 pnpm，如果先让旧记录失效，再发现新记录保存失败，就会两边都没有。因此，对于这种替换，当前实现先保存新记录，再退役旧记录；开启审批时，还要等相关候选获准。

v0.5.1 还修复了一个热安装问题：网页已经创建的空会话，不会再次触发 agent/created。因此加载时除了订阅新事件，还要遍历现有 Agent 补挂提示段，并去重；卸载时关闭存储域，才能再次启用。

这些问题不一定在顺利的演示里出现，所以项目用回归测试和安装验证来检查它们。新版还模拟经过一百八十天和三百六十五天，验证持久记忆，并用真实存储检查重启后标记仍在。这些测试没有调用真实模型。

### 理解与取舍

`prepare` 是包安装流程中的构建入口。Git 仓库保存 TypeScript 源码，而插件运行需要构建出的文件；开发机已经存在的产物会掩盖这类问题。

“先写新、后退役旧”适用于有新候选的替换流程。实现也支持在允许直接生效的情况下仅退役旧事实；不能把“必须永远有新记录”说成所有操作的规则。另外，这个顺序降低了风险，不等于实现了数据库事务或断电后的原子恢复。

如果抽取同时给出多个新候选和多个旧编号，协议没有一一对应关系。当前采用保守办法：同批替代候选全部存在且批准后再退役旧记录。这样减少误退役风险，但会让部分本来可以生效的更新等待更久。

PPT 的 **58+7** 分别是主插件与副插件测试，**19** 是评测器自检；不是 84 次真实模型调用。不能把测试数量当成覆盖所有生产场景的证明。

**衔接：**“更新顺序之外，记忆还需要随时间变化，并能由用户管理。”

## 第 7 页｜记忆更新与可管理性

**记住三个词：用户指定、时间豁免、仍可更新。**

### 口语稿

这里有一个我在准备答辩时发现的问题：一条项目约定可能一直有效，只是很久没再提到。如果仅因为时间过去就把它淡出，助手反而会漏掉有效信息。

所以新版把内容类别和保留策略分开。事实、决策、约定、偏好仍然用于分类；用户可以把任何一条已批准的有效记录指定为持久记忆。普通记录仍按十四、三十、四十五天衰减，持久记录不参与时间衰减。

例如，用户说“把项目统一使用 pnpm 设为持久记忆”，助手先找到具体条目，再调用 memory_pin。以后规则改变，它仍可被替代或删除。持久也不等于每次都放进上下文，相关性和容量限制仍然存在。

### 理解与取舍

“内容类别”回答这条信息是什么，“保留策略”回答它是否随时间淡出。不能因为是 convention 就自动永久保留，也不能认定未固定的信息一定短期有效；由用户明确指定，抽取器不自动设置 pinned。

`memory_pin({id, pinned: true})` 只修改保留标记，不提高基础置信度、不修改记录时间、不隐式批准或复活。`false` 取消持久保留，按原时间恢复衰减，所以一年未强化的旧记录可能立即停止自动注入，工具结果会提示。

普通记忆仍使用 `有效置信度 = 基础置信度 × 0.5^(天数/半衰期)`。14/30/45 天是启发式，没有长期证据说明最优。持久记录直接使用基础分数，但照常经过作用域、审批、退役、相关性和容量检查；分数不是事实正确的概率。

同义合并与强化保留标记；真正替代产生的新记录不继承，用户需要重新指定。这样避免把一个旧条目的授权自动扩大到另一条新规则。持久记录仍可能因模型误判而被错误替代，时间豁免不解决全部准确性问题。

设置和审批工具都可由 Agent 调用，依赖它正确遵循用户意图，不是独立人类认证。只允许操作已批准、未退役记录；默认自动抽取仍不需要审批，`requireApproval` 开启后自动候选需先批准。

**老师追问：这证明长期使用有效吗？** 可以回答：“新增测试只证明程序在模拟时间和重启条件下遵守这些规则。原来 60/60 来自 v0.4.1 的短案例实验，没有验证持久功能或长期准确率。下一步仍需真实长期任务，并比较有效信息漏召回与过期信息误用。”

**衔接：**“下面的效果和成本来自之前 v0.4.1 的真实对照实验，我把它与新增功能测试分开报告。”

## 第 8 页｜实验设计

**记住三个词：统一条件、冻结基线、独立诊断。**

### 口语稿

以下是 v0.4.1 的历史实验。实验设置了三组：没有持久资料的组、读取静态 AGENTS.md 的组，以及使用 dsh-memory 的组。这里特别强调，静态文件一开始是正确的，后续保持冻结。

主实验有二十个预先固定的合成案例，每组每例重复三次，统一回答模型、问题和评分规则。答案表不进入模型输入，执行顺序按固定种子打乱。

另外有四个治理案例，用来检查批准、删除等行为，也各重复三次。它们单独计分，不用来抬高主实验准确率。

这是一组受控实验，目标是分清记忆维护机制的作用，还不是让 Agent 完成完整的真实编程任务。

### 理解与取舍

“冻结”是基线定义，不是偷偷把文件写错。它能观察初始信息后来过期时，自动更新会产生什么差异；代价是无法代表一直有人认真维护的项目说明。因此不能说这项比较已经覆盖了最强的人工维护方案。

几个容易混淆的数量：

| 数量 | 怎么来的 | 代表什么 |
|---|---|---|
| 20 | 预先固定的不同主案例 | 不同题目数 |
| 60/组 | 20 × 3 次 | 每组的作答次数 |
| 180 | 20 × 3 次 × 3 组 | 主对照单元 |
| 12 | 4 × 3 次 | 独立治理诊断单元 |
| 192 | 180 + 12 | 全部单元 |
| 306 | 回答请求＋抽取请求 | 实际模型请求数 |

一个单元可以包含多次模型请求，所以 192 不应等于 306。相同案例的三次重复也不是三个独立案例。

真实 Cordis 和 JSON 后端运行了生产插件，但模型传输与回答上下文由评测器控制。这种安排便于公平比较和复核，也意味着它与完整 CLI 自主任务不同。独立操作视频补充了一次真实网页使用证据，但没有把整个实验自动升级成生产任务评测。

**衔接：**“在这个明确限定的比较范围内，三组结果是什么？”

## 第 9 页｜结果：自动更新减少旧约定残留

**记住三个词：15/51/60、三种变更、有限结论。**

### 口语稿

三组分别答对十五、五十一和六十次，对应百分之二十五、八十五和一百。

我更关注差异来自哪里。插件比静态文件多答对的九次，全部集中在三种约定改变：npm 改成 pnpm、Node 十八改成二十二、周三发布改成周五。三种情况各重复三次，正好是九次。

所以这组结果支持的结论是：在这些变化场景里，自动维护减少了旧约定残留。它不能证明真实项目普遍百分之百准确。无插件组很多时候是因为没有历史资料而回答不知道，也不能把这些拒答说成幻觉。

### 理解与取舍

提升是 **15 个百分点**，即 100% 减去 85%；不要随口说成“提升了 15%”而不说明口径。更直观的说法是“60 次里多答对 9 次”。

反过来看，另外大部分场景静态文件已经很好。插件的优势在本实验中集中于自动处理变化，不是每一道题都更强。恢复原来的发布规则时，冻结文件恰好与最终规则一致，它也答对；这个案例没有被删掉。

“有来源”也不等于“来源内容仍然有效”。静态组能引用 AGENTS.md，同时读出已经过期的规则。记忆维护的价值就在于处理这类有效性变化。

三个重复轮次结果相同，是有限的稳定性观察；不能据此声称统计显著或没有偏差。

**衔接：**“自动更新带来了这部分收益，但它不是没有代价的。”

## 第 10 页｜成本：历史抽取需要额外调用

**记住三个词：额外抽取、5.73 倍、尚未摊销。**

### 口语稿

这页把成本也列出来。静态组在主实验中使用一万零四百五十五个 tokens；插件组使用五万九千九百四十九个，约为静态组的五点七三倍。

主要原因是插件不仅要回答，还要读取历史并抽取记忆。本次插件组有六十次回答，加上九十九次抽取，一共一百五十九次请求。

这个比例是 token 用量比，不是实际账单金额比，也没有算人工维护文件花的时间。因此，我目前只能说自动化换来了一部分更新收益，还不能说它在所有场景都更划算。

### 理解与取舍

token 是模型处理文本的计量单位，大致可理解为文本片段，不要直接当成中文字数。输入、输出、缓存等可能有不同计价方式，因此 token 比不自动等于金额比。

主实验的 59,949 tokens 包括记忆的历史学习成本，不能只保留最后回答那部分来让插件看起来更便宜。反过来，重复读取长期记忆时，前期抽取成本可能被更多后续问题分摊，但本实验没有测这种长期摊销。

正式实验全部用量是 **89,057 tokens / 306 请求**，包含独立治理诊断。操作录像后来产生的调用另算，不要加进去改动原实验数字。

默认的 120 字/90 秒门槛，是减少过密抽取的工程措施：同一会话间隔不足时，增量等下次合格触发，不是后台每 90 秒自动运行一次。正式实验为可控性采用更敏感的触发配置，因此不能把 5.73 倍当成默认长期使用的固定开销。

**衔接：**“结合效果和成本，最后明确这次实验能证明什么、还不能证明什么。”

## 第 11 页｜结果适用范围

**记住三个词：基线有限、样本有限、下一步验证。**

### 口语稿

这次工作的边界主要有三个。

第一，只比较了冻结的静态文件，没有比较持续人工维护的文件。第二，案例是单一模型下的合成短历史，没有独立留出集。第三，它不是完整编程任务评测，不能直接说明能提高真实开发效率。

另外，九十六条新增候选的内容复核由 AI 完成，不是独立人工标注。

新版持久功能目前只有确定性时间与存储验证，不能用旧实验分数证明其长期效果。如果继续推进，我会优先增加独立真实项目任务、持续维护的静态基线和人工复核，再测默认配置下的长期成本。这样才能知道，这个自动维护机制在什么场景下值得使用。

### 理解与取舍

“留出集”是开发和调试时不使用、最后才拿来检验的另一批案例。没有它，就应承认设计过程可能对现有案例有偏向。

“AI 审阅没有发现无支持候选”不是“幻觉率为零”。它不等于独立人工判断，也没有衡量漏掉了多少该记的信息。不要把候选审阅和问题回答准确率合并成一个万能分数。

这里主动说明局限，是把结论说到证据能支持的位置。回答老师时可以用这个顺序：“目前验证了什么 → 没验证什么 → 如何补验证”，不必只说“这是缺点”。

未来可以考虑 embedding 检索、独立授权或重试队列，但本次结论并不依赖于把它们说成已经实现。

**衔接：**“最后说明这次工程中我与 AI 的分工，以及已经交付的内容。”

## 第 12 页｜单人组与 AI 协同开发

**记住三个词：真实分工、主项目贡献、已交付。**

### 口语稿

这是一个单人组的 AI 协同开发项目。我负责选题和范围决策、配置凭证、运行真实评测、审阅展示方向，并负责最终提交和今天的汇报。AI 参与了源码研究、实现、测试、结果复核和材料生成。

另外做了一个小型配套插件 dsh-commit，根据暂存区差异生成中文提交说明，用来验证同一套插件接口的复用，这里不展开。

这次工作的主要产出，是一个可安装、可管理、能跨会话保存项目约定的插件，以及一组同时呈现收益、成本和局限的实验。源码、网站、PPT、操作视频和评测报告都已整理完成。谢谢老师。

### 理解与取舍

现场汇报时“今天的汇报”成立；练习时可照读，但不要把尚未发生的课程平台提交说成已经完成。

不要说“所有代码都是我独立写的”，也不必因为用了 AI 就回避工程细节。你需要能解释方案为何成立、哪些证据可信、哪些结论不能外推。老师追问时，选自己真正理解的一个问题讲透，例如“为什么先写新记录再退役旧记录”。

dsh-commit 只生成提交文字，本身不执行 git commit 或推送。它是独立配套插件，不是 dsh-memory 的必需依赖，也不是本次主评测对象。

## 上台前五个理解检查

合上稿子，用自己的话回答：

1. 关掉会话再打开后，模型为什么还能知道 pnpm？答到“磁盘记录 → 新上下文注入”，而不只是“因为有记忆”。
2. 为什么不把整段聊天永久加入每次请求？答到长度与调用成本、重复/过期信息、可管理性；也承认抽取会丢失细节。
3. npm 改 pnpm 时，为什么去重和更新顺序会冲突？答到两句话很相似，不能把新规则误当作旧规则的重复；先排除旧目标，再写新记录。
4. 为什么不能用 60/60 宣称比人工维护 AGENTS.md 好？答到基线是冻结文件、只有 20 个合成案例，没有测人的持续维护。
5. 为什么成本更高还值得研究？答到减少维护劳动的可能收益与额外调用的代价；是否值得仍需场景与长期证据。
